# Feature: stacked Filament panels for tenant hierarchy

Each tenant level runs in its own Filament panel. Switching context swaps the panel and the whole sidebar. Pattern must generalise to a future workspace level without rewriting.

## Scope (first cut)

Two panels: `OrganizationPanelProvider` and `ProjectPanelProvider`, both extending an abstract `BasePanelProvider` that carries shared brand, colors, middleware, plugins, and auth wiring.

- `OrganizationPanel` — path `/`, tenant `Organization`, URL `app.{host}/{org}/...`.
- `ProjectPanel` — path `/{org}`, tenant `Project`, URL `app.{host}/{org}/{project}/...`. Resolves `{org}` from the leading path segment in panel middleware and binds it.

Same `User`, per-panel `canAccessPanel()`, per-panel resource discovery. `BelongsToOrganization` and `BelongsToProject` traits read whichever tenant is active.

## Auth

Shared Laravel `web` guard + session cookie — login once, authenticated everywhere. Only `OrganizationPanel` enables `->login()`; `ProjectPanel` registers `Authenticate` middleware and redirects unauthenticated requests to the org-panel login. `canAccessPanel()` decides admittance per panel (deny = 403, no re-prompt).

## Out

Workspaces, `admin` panel changes.

## Open

- Org chip in project-panel topbar — shared Livewire or per-panel render.
- Cross-panel URL generation — currently `route('filament.project.pages.dashboard', ['organization' => ..., 'tenant' => ...])` is the only working path because Filament's `Panel::getUrl()` literal-concatenates the panel `path`, which breaks for `'{organization:slug}'`. Decide whether to add a `panelUrl()` helper that wraps this, or push upstream for parameterised `path()` support.

## Built

- Project selector in org-panel topbar — `App\Livewire\ProjectMenu` renders a Blade that mirrors `vendor/filament/filament/resources/views/components/tenant-menu.blade.php` (same `x-filament::dropdown`, same `fi-tenant-menu*` classes for CSS reuse, same `<x-filament-panels::avatar.tenant>` primitive, same `generate_icon_html` chevron). Direct reuse of `<x-filament-panels::tenant-menu />` isn't viable — it reads `filament()->getTenant()` / `getUserTenants()` for the current panel, which always resolve to orgs in this context. Data comes from `App\Services\ProjectMenuResolver` (projects list + per-project avatar URL via `Filament::getTenantAvatarUrl()` + create URL). Hooked via `PanelsRenderHook::TENANT_MENU_AFTER`.
- Organization selector in project-panel topbar — symmetric counterpart. `App\Livewire\OrganizationMenu` + `App\Services\OrganizationMenuResolver`, same Blade pattern. Hooked via `PanelsRenderHook::TENANT_MENU_BEFORE` so the org sits above the project switcher.
- Project create flow — `App\Filament\Organization\Resources\Projects\ProjectResource` on the org panel. Form is just `name` (slug auto-generated by `HasSlug`; `organization_id` auto-set by Filament's tenant-ownership relationship on `Organization::projects()`). `CreateProject::afterCreate()` attaches the creating user as a project member.

## Acceptance

URL alone determines context. Wrong-org / wrong-project slug 404s. Adding a `workspace` panel under `/{org}/{project}/{workspace}` requires only a new provider extending `BasePanelProvider` + middleware.
